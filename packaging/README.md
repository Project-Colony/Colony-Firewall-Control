# Packaging

Everything a package ships, at a glance:

| File (repo)                          | Installed to                                              |
| ------------------------------------ | --------------------------------------------------------- |
| `colony-firewalld`, `colony-firewall`, `colony-firewall-tray`, `cfc` | `/usr/bin/`               |
| `packaging/systemd/colony-firewalld.service`   | `/usr/lib/systemd/system/`                                |
| `packaging/systemd/colony-firewall-nft.service`| `/usr/lib/systemd/system/`                                |
| `packaging/systemd/colony-firewall-nft-inbound.service` | `/usr/lib/systemd/system/`                       |
| `packaging/systemd/colony-firewall.sysusers`   | `/usr/lib/sysusers.d/colony-firewall.conf`                |
| `packaging/systemd/daemon.toml.sample`         | `/etc/colony-firewall/daemon.toml` (config, never clobbered) |
| `packaging/systemd/nftables-snippet.conf`      | `/usr/share/colony-firewall/nftables-snippet.conf`        |
| `packaging/systemd/nftables-inbound.conf`      | `/usr/share/colony-firewall/nftables-inbound.conf`        |
| `scripts/inbound-lockout-guard.sh`   | `/usr/lib/colony-firewall/inbound-lockout-guard.sh`       |
| `packaging/linux/colony-firewall.desktop`        | `/usr/share/applications/`                                |
| `packaging/linux/colony-firewall-autostart.desktop` | `/etc/xdg/autostart/colony-firewall.desktop`           |
| `packaging/linux/colony-firewall-tray-autostart.desktop` | `/etc/xdg/autostart/colony-firewall-tray.desktop` |
| `assets/icons/colony-firewall.svg`            | `/usr/share/icons/hicolor/scalable/apps/`                 |
| `README.md`, `docs/{ARCHITECTURE,HARDENING,TROUBLESHOOTING}.md`, `docs/guide/first-run.md` | `/usr/share/doc/colony-firewall-control/` |
| `LICENSE`                            | `/usr/share/licenses/colony-firewall-control/`            |
| generated by `cfc`                   | completions in `/usr/share/{bash-completion/completions,zsh/site-functions,fish/vendor_completions.d}/`, man pages in `/usr/share/man/man1/` |
| `cfc-ebpf.o` (built by `cargo xtask build-ebpf`) | `/usr/lib/colony-firewall/`, release tarball only; the AUR and RPM packages deliberately do not ship it (see `DEFAULT_OBJECT_PATH` in `crates/cfc-daemon/src/ebpf/mod.rs`), and the daemon degrades to `sock_diag` + `/proc` attribution without it |

Key design points:

- **`colony-firewall-nft.service`** makes enforcement persistent
  (`nft -f` the snippet on start, `nft delete table inet colony_firewall`
  on explicit nft-unit stop). The table survives daemon restarts and stops,
  so new non-loopback flows fail closed while its queue listener is absent. Upgrades reload
  active nft units atomically and leave inactive inbound filtering opt-in.
  The daemon requires this unit before initialization. Enabling either nft
  unit creates native `Requires` links from NetworkManager and
  systemd-networkd, ordered after nft loading; load failure blocks those
  managers' startup. Enabling the daemon also enables outbound enforcement.
  Upgrade scripts reenable enabled nft units to create those links.
  Explicit disable and uninstall remove them. The units load after a
  distribution `nftables.service` in the same boot transaction. This contract
  excludes initramfs networking, already configured interfaces, other network
  managers and later external ruleset flushes.
- **`colony-firewall.sysusers`** creates the `colony-firewall` group used
  to gate access to the daemon's gRPC UNIX socket. Users join with
  `usermod -aG colony-firewall <user>`. Membership gives read access and
  lets the installed app and tray connect; changes come from those two
  programs or from `sudo cfc`.
- **`org.projectcolony.firewall.policy`** declares the polkit actions the
  daemon asks about when the app or tray pauses, resumes, imports rules or
  stores an Allow rule that names no program (`auth_admin` for pause and
  resume, `auth_admin_keep` for the others). Installed to
  `/usr/share/polkit-1/actions/`; polkit is an optional dependency, and
  without it only `sudo cfc` can do those.
- **XDG autostart** launches the GUI in every desktop session so prompts
  actually reach the user. Per-user opt-out: copy the file to
  `~/.config/autostart/` and set `Hidden=true`.

## Arch Linux (AUR)

`PKGBUILD` is the release recipe: it builds from the GitHub tag tarball
(`v$pkgver`) and is AUR-submittable.

**The `sha256sums=('SKIP')` in the checked-in file is a placeholder and
must never be published.** `SKIP` on a non-VCS remote source disables
integrity checking of the downloaded tarball entirely, which is not
acceptable AUR practice. `updpkgsums` replaces it; the `pkgbuild` job in
`.github/workflows/release.yml` runs `updpkgsums` against the tag, asserts
the placeholder is gone, builds the package, and the release publishes the
resulting `PKGBUILD` and `SRCINFO`, signed like every other asset - so the
recipe can be downloaded from the release instead of regenerated by hand.
The `SRCINFO` asset is deliberately undotted: GitHub renames dot-leading asset filenames
(a `.SRCINFO` upload was published as `default.SRCINFO`, which no
pattern anyone would guess could download). Rename `SRCINFO` to
`.SRCINFO` when copying it into the AUR checkout - the AUR rejects a
push without a file of exactly that name. Releases up to v0.2.3
carry the old `default.SRCINFO` spelling.

The checksum `updpkgsums` writes is trust on first use: it is the hash of
whatever GitHub served for `archive/v$pkgver.tar.gz` when the tag was built,
and nothing compares that archive with the tagged tree. How to check the
signature of a release asset is under
[Code signing policy](../README.md#code-signing-policy).

Nothing in a release is bumped or tagged by hand (see
[Releases](#releases)). Publishing to the AUR stays a manual step, from the
assets of the published release:

```sh
V=X.Y.Z
work=$(mktemp -d) && cd "$work"
# 1. The recipe CI built against the tag, with the real source checksum.
#    Verify both files first (README.md, Code signing policy).
gh release download "v$V" -R Project-Colony/Colony-Firewall-Control \
    -p PKGBUILD -p SRCINFO -p 'PKGBUILD.*' -p 'SRCINFO.*'
# 2. The install scriptlet is not a release asset; take it from the tag.
curl -fsSLO "https://raw.githubusercontent.com/Project-Colony/Colony-Firewall-Control/v$V/packaging/arch/colony-firewall-control.install"
# 3. Test build.
makepkg -si
namcap PKGBUILD ./*.pkg.tar.zst        # no E: lines
# 4. Push to the AUR.
git clone ssh://aur@aur.archlinux.org/colony-firewall-control.git aur
cp PKGBUILD colony-firewall-control.install aur/ && cp SRCINFO aur/.SRCINFO
cd aur && git add -A && git commit -m "Update to $V" && git push
```

Note that only `PKGBUILD`, `.SRCINFO` and `colony-firewall-control.install`
belong in the AUR repository - `.gitignore` everything else `makepkg`
leaves behind.

The install scriptlet (`colony-firewall-control.install`) prints first-run
steps on install (enable units, `sudo cfc rules bootstrap-defaults`, join
the `colony-firewall` group) and, critically, its `pre_remove` stops
`colony-firewall-nft` + `colony-firewalld` and deletes
`table inet colony_firewall`, so removing the package can never leave the
fail-closed queue rule behind and blackhole outbound traffic.

Shell completions and the man pages are not shipped as source: `package()`
generates them by running the `cfc` it just built (`cfc completions
<shell>`, `cfc man --dir`), so they cannot drift from the CLI. Neither
subcommand talks to the daemon, so this works in a clean chroot.

### -git developer variant

`PKGBUILD-git` builds `colony-firewall-control-git` from the git HEAD with
a `pkgver()` derived from `git describe` (e.g. `0.1.0.r5.gabc1234`, or
`r42.abc1234` before the first tag). It `provides`/`conflicts` the release
package. To iterate on a local checkout instead of GitHub, set
`_giturl="git+file:///path/to/Colony-Firewall-Control"` at the top of the
file. Usage is documented in its header comment.

This is the recipe CI actually builds: the `pkgbuild-build` job in
`.github/workflows/check.yml` points `_giturl` at the checkout and runs a
full `makepkg` on every push and pull request, so `build()`, `package()`
and the install scriptlet are exercised without needing a published tag.
`packaging-lint` in the same workflow covers the static side (`bash -n`,
sourceability, `makepkg --printsrcinfo`, `namcap`, `shellcheck` on the
scriptlet) for both recipes.

## Release tarball

The release attaches `colony-firewall-control-<V>-linux-x86_64.tar.zst`, the
only channel that ships `cfc-ebpf.o`. Install and remove it by hand, as root:

```sh
tar --zstd -xf colony-firewall-control-<V>-linux-x86_64.tar.zst
cd colony-firewall-control-<V>-linux-x86_64
sudo ./install.sh      # then First run in first-run.md
sudo ./uninstall.sh
```

Verify the download first, as described under
[Code signing policy](../README.md#code-signing-policy).

Both scripts are generated by `scripts/tarball-installers.sh` from
`packaging/tarball-manifest.json`, the tarball's install recipe. It is not
the Colony manifest (see [Colony](#colony)): Colony installs a single
per-user binary and runs no scripts, so it could not install units, nft
tables or the sysusers group anyway.

- `postInstall` is **idempotent**: `daemon.toml` is only installed if
  absent, so upgrades never clobber user config. `install.sh` runs it
  after copying `binaries` to `installPath`.
- `preRemove` mirrors the pacman `pre_remove`: disable and stop the units,
  delete both Colony nft tables and `/sys/fs/bpf/colony-firewall`, then
  remove the files `postInstall` placed (user config in
  `/etc/colony-firewall/` is kept). `uninstall.sh` runs it and then removes
  the binaries.

The tarball is built by the `build` job in
`.github/workflows/release.yml`, which is the source of truth for its
contents. It unpacks to a single
`colony-firewall-control-<V>-linux-x86_64/` directory, and inside that
the layout is **flat**: `install.sh` runs from the extracted directory, so
every file `postInstall` names must sit directly in it under exactly that
basename.

`scripts/check-release-assets.sh` (a hard gate in `check.yml`, re-run in
`release.yml`) parses this manifest's `postInstall` commands and fails if
any source they install is not staged by the workflow. Adding a line to
`postInstall` without adding the file to the workflow is therefore a CI
failure rather than a silent gap in tarball installs, which is how
the `colony-firewall.sysusers` fragment previously went missing, leaving
no `colony-firewall` group and a root-only control socket.

To reproduce the tarball locally, from the repo root:

```sh
cargo build --workspace --release --locked
cargo xtask build-ebpf   # cfc-ebpf.o; install.sh fails outright without it

V="$(sed -n 's/^version = "\([^"]*\)".*/\1/p' Cargo.toml | head -n1)"
NAME="colony-firewall-control-${V}-linux-x86_64"
STAGE="$(mktemp -d)/${NAME}"
mkdir -p "${STAGE}"

install -m755 \
    target/release/colony-firewalld \
    target/release/colony-firewall \
    target/release/colony-firewall-tray \
    target/release/cfc \
    scripts/inbound-lockout-guard.sh \
    "${STAGE}/"

install -m644 \
    packaging/systemd/colony-firewalld.service \
    packaging/systemd/colony-firewall-nft.service \
    packaging/systemd/colony-firewall-nft-inbound.service \
    packaging/systemd/colony-firewall.sysusers \
    packaging/systemd/daemon.toml.sample \
    packaging/systemd/nftables-snippet.conf \
    packaging/systemd/nftables-inbound.conf \
    packaging/linux/colony-firewall.desktop \
    packaging/linux/colony-firewall-autostart.desktop \
    packaging/linux/colony-firewall-tray-autostart.desktop \
    assets/icons/colony-firewall.svg \
    packaging/linux/org.projectcolony.firewall.policy \
    "${STAGE}/"

install -m644 \
    crates/cfc-ebpf/target/bpfel-unknown-none/release/cfc-ebpf.o \
    "${STAGE}/"

install -m644 \
    README.md CHANGELOG.md LICENSE \
    docs/ARCHITECTURE.md docs/HARDENING.md docs/TROUBLESHOOTING.md \
    docs/guide/first-run.md \
    "${STAGE}/"
./scripts/tarball-installers.sh "${STAGE}"

tar --zstd -C "$(dirname "${STAGE}")" -cf "${NAME}.tar.zst" "${NAME}"
```

This mirrors the workflow's `Assemble tarball` step file for file. If
the two ever disagree, the workflow wins - it is the copy
`scripts/check-release-assets.sh` gates against the manifest, this one
is not - so fix this list to match it.

## Colony

`colony.json` at the repository root lists the app in
[Colony](https://github.com/Project-Colony/Colony) under Security. Colony
downloads the `colony-firewall-control-linux` release asset, which is the
app (`colony-firewall`), into the user's own directory and runs nothing as
root. So it installs neither the daemon nor the units, the polkit policy or
the `colony-firewall` group, and the daemon treats that copy as read-only:
it accepts changes only from the root-owned `/usr/bin/colony-firewall` and
`/usr/bin/colony-firewall-tray` (`[ipc] official_clients`). With the
daemon installed from the AUR, the RPM or the tarball, the Colony copy
monitors it, and shows the daemon's reason when it refuses a change.

## Releases

Releases are cut by release-please. Every push to `main` updates its
release PR from the conventional commits merged since the last release.
Merging that PR bumps the version in `Cargo.toml`, both `Cargo.lock` files,
`packaging/arch/PKGBUILD`, `packaging/rpm/colony-firewall-control.spec` and
`packaging/tarball-manifest.json` (`extra-files` in
`release-please-config.json`), writes the `CHANGELOG.md` section, and tags
`vX.Y.Z`. `scripts/check-versions.sh` fails CI on the release PR if a file
was missed. The spec's `%changelog` is the one place release-please does
not write; rpmlint only warns about it.

The tag then runs `.github/workflows/release.yml`, while the release is
held as a draft:

1. `build` builds the workspace and the eBPF object from the tag, checks
   `colony.json` with `colony validate-manifest` against the asset names,
   runs `--version` on all four binaries and assembles the tarball.
2. `pkgbuild` builds the release `PKGBUILD` against the tag's source
   archive in an Arch container.
3. `attest` records build provenance for the Linux binary and the tarball.
4. `sign-and-publish`, the shared workflow of Project-Colony-Resources,
   signs every asset with the organisation key (`.sig`, `.meta`,
   `.meta.sig`), uploads, downloads again, verifies, and only then
   publishes the release.

The published assets:

| Asset | What it is |
|---|---|
| `colony-firewall-control-linux` | the app, under the name Colony installs |
| `colony-firewall-control-<V>-linux-x86_64.tar.zst` | the release tarball described above |
| `SHA256SUMS` | sha256 of the two files above |
| `PKGBUILD`, `SRCINFO` | the Arch recipe with the tag's source checksum |

each with its `.sig`, `.meta` and `.meta.sig`. When a run fails after the
tag exists, fix the cause and finish the draft from the tag:
`gh workflow run release.yml --ref vX.Y.Z -f tag=vX.Y.Z`.

## Manual install

Follow [docs/guide/first-run.md](../docs/guide/first-run.md): its Manual
install section, then First run: enable enforcement, then seed the starter rules with
`sudo cfc rules bootstrap-defaults` right away. `sudo` is required there: a
non-root `cfc` is read-only, whatever its groups, and until the rules exist,
unmatched DHCP, DNS and NTP flows are denied.

## Uninstall behavior (all channels)

Order matters because the nftables snippet is fail-closed:

1. `systemctl disable --now colony-firewall-nft-inbound colony-firewall-nft colony-firewalld`
   (stopping the nft unit runs `nft delete table inet colony_firewall`).
2. Delete `table inet colony_firewall` and `table inet colony_firewall_inbound`
   if still present, in case either was loaded manually.
3. Remove `/sys/fs/bpf/colony-firewall` so pinned kernel denials cannot outlive
   uninstall.
4. Remove files. `/etc/colony-firewall/daemon.toml` is user config and is
   left behind (pacman saves it as `.pacsave`).

The AUR package does this automatically via `pre_remove`, the RPM via
`%preun`/`%postun` and the release tarball via `uninstall.sh`; manual
installs should follow the steps above.
